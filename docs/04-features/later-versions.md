# Функц. требования: v2–v6 (направления)

Глубина детализации убывает с номером версии (§8): v2 — как требования, v3–v6 — направления
с фиксацией **точек интеграции**. Принцип: каждая версия встраивается в ядро **без переписывания**.
Детальные спеки пишутся ближе к делу.

---

## v2 — Коммуникация и оркестрация (§8.2)
- **Чаты**: каналы (public/private), DM, треды, упоминания, реакции, вложения; presence/«печатает»; непрочитанные; `ChatWidget` на дашбордах. → новые `Channel`/`Message`; presence уже есть ([realtime](../02-architecture/realtime.md))
- **Митинги**: создание, участники, привязка к issue/project, заметки (doc), опц. запись.
- **Календарь событий (отдельный Section, персональный)** — НЕ путать с MVP task-календарём (issues по датам, §8.1.6, уже есть). Это полноценный календарь человека:
  - Отдельный пункт в левом рейле `Calendar` (персональный): показывает события/митинги/релизы пользователя, а не задачи.
  - Сущность `CalendarEvent`: `title`, `starts_at`/`ends_at` (datetime), `all_day` (bool), `type` (`meeting` | `event` | `release` | `reminder` | `ooo`), `rrule` (повтор RFC-5545), `scope` (`personal` | `team` | `workspace`), опц. `issue_id`/`project_id` (привязка, напр. дата релиза проекта), `location`/`url`, `color_token`.
  - Сущность `Meeting` (как часть событий type=meeting): участники, attendance, заметки (doc), опц. ссылка на запись.
  - **Релиз-маркеры**: события type=release (общие/командные) — видны всей команде/воркспейсу.
  - Виды: месяц / неделя / день; список «сегодня/неделя».
  - Двусторонняя синхронизация с задачами: `due_date`/`scheduled_date` issue могут проецироваться как события (оверлей, опц.); событие → может создавать/линковать issue.
  - Внешние календари (Google/Microsoft) — v5 (интеграции).
  - Скоуп: личные события (per-user) + командные/общие (релизы, командные митинги). RLS по `workspace_id` + видимость по scope.
- **Двусторонняя синхронизация календаря/задач**: события ↔ issues; митинги в календаре. → CalendarRenderer (task-вариант) уже есть; событийный — новый
- **Command palette** (Cmd-K) полный: навигация/действия/создание/переключение (базовый — в MVP).
- **Совместное редактирование доков** (CRDT/Yjs) — кандидат сюда (ADR-0004 #9). → `Document.body` изолирован под замену LWW→CRDT
- **Timeline/Gantt renderer** — ранний v2 (ADR-0004 #4). → контракт renderer'а уже допускает (§6.3)

**Точки интеграции:** presence/WS, виджеты дашборда (`type` расширяется chat/doc/embed), renderer-реестр.

## v3 — Git и связка с кодом (§8.3)
- Собственные **репозитории** (хостинг git), браузер кода, ветки, PR/MR, ревью.
- **Пайплайны** (CI): описание, запуск, статусы, логи; изолированные раннеры.
- **git ↔ issues/projects**: парсинг `KEY-N` в коммитах/ветках/PR → автосвязь и автопереходы статусов; PR как attachment с живым статусом. → `Attachment.meta.live-статус` уже заложен ([issues](../01-domain/issues.md))
- Архитектурно: git-хостинг и CI-раннеры — **первые кандидаты на выделение в сервисы** ([modules](../02-architecture/modules.md) §5).

**Открытое решение #6:** свой git-хостинг vs обёртка над Gitea/GitLab — [open-questions](../open-questions.md).

## v4 — Dev-окружение внутри платформы (§8.4)
- **Тайм-трекеры**: ручной/таймер, оценка vs затрачено, отчёты, биллинг-флаг. → новый `TimeEntry`
- **Web IDE для git** (Monaco/code-server), привязка к репозиториям.
- **Менеджер SSH-соединений**: каталог, безопасное хранение ключей (через secret store).
- **Хранилище secrets**: шифрование app-level + KMS, скоупы (workspace/team/project), аудит, инъекция в пайплайны/IDE. → §9.3

## v5 — Экосистема и интеграции (§8.5)
- Внешние интеграции: GitHub/GitLab, Slack, AI-провайдеры, календари (Google/MS), Figma. → `Integration`/`IntegrationInstall`/`Webhook`
- **Публичный API** (REST/GraphQL) + webhooks; OAuth-приложения; маркетплейс. → **открытое решение #8**
- Импорт из Linear/Jira/ClickUp (миграция данных). → глоссарий-маппинг (§2) — основа
- **RabbitMQ** включается как событийная шина наружу ([modules](../02-architecture/modules.md) §2).

## v6 — MCP и собственная AI (§8.6)
- **MCP-сервер**: экспонирование сущностей/действий как инструментов для агентов — ложится на наш command/query слой ([commands](../02-architecture/commands.md)).
- **Собственная AI**: ассистент (поиск/саммари/авто-триаж/генерация); агентные действия через `AiAction` — предложение мутации, требующее подтверждения (safety-gate). → **открытое решение #7**
