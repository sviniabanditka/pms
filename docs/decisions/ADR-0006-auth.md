# ADR-0006 — Аутентификация: opaque-токены в Redis

- Статус: accepted
- Дата: 2026-06-27
- Связано: §7.2 (Auth), [identity-access](../01-domain/identity-access.md), [realtime](../02-architecture/realtime.md)
- Mechanics: [`../02-architecture/auth.md`](../02-architecture/auth.md)

## Контекст

SaaS, серверные сессии (ADR-0001). Нужен метод аутентификации для REST/Connect и WS-апгрейда.
Развилка: opaque-токены (серверные сессии в Redis) vs JWT.

## Решение

**Opaque-токены, сессии в Redis.** Токен — непрозрачный случайный идентификатор; состояние сессии
(user_id, expiry, метаданные) в Redis.

## Почему

- **Мгновенный отзыв**: logout/бан/смена пароля = удалить ключ. Критично для долгоживущих WS-соединений и банов (JWT потребовал бы blacklist → тот же Redis, но сложнее).
- Redis уже в горячем пути (cache/pub-sub/presence) — чтение сессии не добавляет инфраструктуры.
- Проще ротация/инвалидация, нет проблемы «протухший, но валидный по подписи JWT».

## Последствия

- Проверка токена = lookup в Redis (быстро); кэш в памяти инстанса с коротким TTL допустим.
- WS-апгрейд аутентифицируется тем же токеном; разрыв при отзыве сессии.
- OAuth/SAML/SCIM/2FA — позже (§7.2), поверх той же сессионной модели.
