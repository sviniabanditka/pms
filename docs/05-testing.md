# Стратегия тестирования

Тестирование закладывается с архитектурой. TDD-узлы: доменная логика, движок фильтров,
политики прав, редьюсеры стора (§10). Самый критичный контракт — **три реализации Filter AST**.

---

## 1. Пирамида и зоны

| Уровень | Что покрываем | Инструменты |
|---|---|---|
| **Unit** | переходы по категориям статусов, нумерация, fractional ordering, зеркала relations, **исполнение Filter AST**, RBAC-политики, редьюсеры/мутации стора | go test/testify, Vitest |
| **Integration** | команды end-to-end (validate→authz→tx→дельта), компиляция Filter AST в SQL/OpenSearch, миграции, River-джобы | go test + testcontainers-go |
| **Contract** | **эквивалентность Filter AST: client vs SQL vs OpenSearch**; схемы команд фронт↔бек (proto); публичный API (v5) | property-based, schema-проверки |
| **Component (UI)** | renderers (Board/List/Table/Calendar), доменные компоненты, виджеты | Vue Test Utils/Testing Library + Vitest |
| **E2E** | критические сценарии (§2 ниже) | Playwright |
| **Realtime/Multi-client** | синхронизация двух клиентов, разрешение конфликтов, догон после оффлайна | Playwright (2 контекста) + WS-нагрузка |
| **Performance** | большие воркспейсы (сотни тыс. issues), виртуализация, пропускная способность синка | k6/Gatling, Lighthouse |
| **Visual regression** | стабильность минимал-UI и токенов | Playwright screenshots |
| **Accessibility** | клавиатура, фокус, ARIA, контраст | axe-core в E2E |

## 2. Критические E2E-сценарии (минимум, §10.2)
1. Создание команды → issue → корректный `KEY-N`.
2. Board: drag issue между статусами → проверка `started_at`/`completed_at` и порядка.
3. Фильтр+группировка+сортировка → сохранение View → переоткрытие → консистентность.
4. Календарь: drag issue на дату → смена `scheduled/due` → отражение в списке.
5. Cycle: добавление issues → корректные scope/burndown.
6. Дашборд: ViewWidget с фильтром → совпадение с полноэкранным View.
7. Real-time: изменение в клиенте A мгновенно в B; оффлайн-правка догоняется.
8. Права: guest не видит private-команду; member видит public-дочернюю.

## 3. Особое внимание (§10.3)
- **Filter AST** — двойная/тройная реализация ⇒ **property-based контрактные тесты обязательны**: генерируем случайные валидные AST + наборы данных, сверяем результаты трёх движков. Относительные даты резолвятся детерминированно (§query-engine 3.2) — иначе тест флапает.
- **Синхронизация/конфликты** — одновременные мутации одних полей (per-field LWW), потеря/восстановление соединения, **идемпотентность** повторно отправленных команд (по `command.id`).
- **Нумерация под нагрузкой** — конкурентное создание issues в одной команде → отсутствие коллизий номеров (row-lock на `teams.next_issue_number`).
- **RBAC** — наследование при вложенности (inherit-public vs strict), инжекция видимости в запросы (нельзя «отфильтровать» недоступное).

---

## 4. Тестовые данные и среды (§10.4)
- Детерминированные сид-фабрики (реалистичные объёмы для perf); анонимизированные снапшоты для воспроизведения багов.
- Изоляция через Docker/testcontainers-go; ключевые наборы в CI на каждый PR; тяжёлые (perf/visual) — по расписанию/на релиз-ветке.
- Бюджеты бандла/TTI фиксируются и контролируются в CI (§9.1).

## TDD-узлы (писать тест первым)
Переход статуса (категории), fractional ordering, зеркала relations, `match()` Filter AST,
per-field LWW merge, RBAC policy, нумерация.
